Boxmegle · fight telemetry

What the fight data can tell us.

A catalog of every visualization worth building from a Boxmegle match — and, because packages/game-mechanics is still a stub, a specification of the event log that has to exist underneath them. Every chart on this page is rendered against one synthetic 90-second fight, so the numbers agree with each other the way real ones would.

Synthetic fight · deterministic seed 509

The constraint

Speed and timing only. No punch classifier.

Everything here derives from four measurements: wrist velocity, when a punch happened, which hand threw it, and how high the guard was. No jab/cross/hook/uppercut typing, no target detection. That constraint is what makes this buildable in a hackathon — and it turns out to cost far less than you'd expect.

The rule that unlocks everything

A punch lands if the opponent's guard was down at that timestamp. Damage is a function of peak wrist speed.

Both clients already stream guard height over /game_session, so hit detection needs no classifier and no shared coordinate space — which is just as well, since the two fighters are on separate webcams and share no physical geometry at all. This single rule yields accuracy, damage, health curves and momentum: the entire narrative spine of the summary page. It also promotes guard from a cosmetic readout to a real mechanic, and it's symmetric, so neither player can exploit it.

Prerequisite · non-negotiable

Normalize every distance by shoulder width, per frame.

Without it, a player who sits closer to their webcam punches harder forever, and every number on this page becomes a measure of desk depth. Store speeds in shoulder-widths per second; convert to mph only for display, because "31 mph" lands and "4.2 sw/s" does not.

Known limitation · found while building these charts

A binary guard rule makes your accuracy a measurement of your opponent, not of you.

If landed is exactly "their guard was down", then 100% of the punches you absorb arrived while you were exposed — by construction. Any chart claiming that as an insight is quoting its own definition back at you, and accuracy stops being a skill stat: throw with your eyes closed and you'll score the same. The fix is small. Make guard continuous, which it already is, and scale damage by peakSpeed × (1 − opponentGuard) — then your speed still matters against a high guard, chip damage exists, and accuracy becomes a real distribution instead of a coin weighted by someone else. The charts on this page work either way; this one is a gameplay decision, not a visualization one.

Surface 01 · post-fight

The summary page

The richest surface: the whole event log is already client-side, there's no latency budget, and the player is finally sitting still. This is where the fight gets explained back to them.

Surface 02 · live

The in-fight HUD

One rule governs this whole surface: no charts during the fight. A fighter mid-exchange can read a bar and one big number in peripheral vision. Anything else is decoration they will never look at.

Health bars

The only element that is genuinely non-negotiable. Corner-coloured, mirrored to each fighter's own side of the screen.

Speed flash

Peak mph over your own feed on impact, 400 ms fade. The single most satisfying number in the game — make it big.

Burst counter

Increments inside the 600 ms window, resets after 1.5 s of silence. Same computation as the burst chart, live.

Stamina ring

Depletes with output rate, regenerates when you pause. A real mechanic derived from cadence alone — it makes the fatigue curve something the player chose.

Exposure vignette

Red pulse at the frame edge after 1 s of guard down. Diegetic and preattentive — no UI chrome, readable without looking at it.

Surface 03 · persistent

The fighter profile

What survives the match and accumulates in users.record and users.max_stats. This is the surface that makes people come back, and every axis of it is derivable from speed and timing.

Surface 04 · meta

The player pool

Nearly free once the hot-tier stats exist — these are single indexed queries, not blob reads. Worth building because they're the only thing that gives a stranger's match a scale to sit on.

What it all demands

The schema this implies

Every requires chip above is a claim about a field the fight loop has to emit. Collected, they specify the event log — and they split cleanly into two storage tiers with very different access patterns.

Tier 1 · hot

Postgres — queryable

Pre-aggregated per-player match stats. Powers the KPI tiles, the whole profile surface, and every leaderboard without touching the replay blob.

  • Best as a match_player_stats table — two rows per fight — so leaderboards are indexable. A jsonb column on completed_games works but can't be indexed usefully.
  • Gives the currently-undefined users.record and users.max_stats a shape at last.
  • Roughly 400 bytes per fighter per fight.
Tier 2 · cold

Supabase Storage — one blob

Full frame log plus punch events under the existing replay_key. Fetched exactly once when the summary page mounts.

  • Powers the fight tape, the momentum ribbon, every time series, and the 3D reconstruction.
  • 33 landmarks × 3 axes × 30 fps × 90 s ≈ 1.4 MB as float32.
  • Quantize normalized coordinates to int16 → ≈ 350 KB. Store as a packed typed array with a small JSON header, never as JSON numbers.
// packages/game-mechanics/types.ts
// Cold tier — one entry per detected punch.
export type PunchEvent = {
  t:          number   // ms from fight start
  hand:       'L' | 'R'
  peakSpeed:  number   // shoulder-widths / sec — NEVER pixels
  extension:  number   // max wrist→shoulder distance, shoulder-widths
  retractMs:  number   // time back to guard; low = tight technique
  landed:     boolean  // opponent.guard < threshold at t
}

// Cold tier — one entry per captured frame, ~30 Hz.
export type FrameSample = {
  t:             number
  lm:            Int16Array  // 33 landmarks × 3, normalized then quantized
  guard:         number      // 0..1, wrist_y vs shoulder_y
  shoulderWidth: number      // px — the scale factor everything divides by
}

// Hot tier — what lands in Postgres. One row per fighter per fight.
export type MatchPlayerStats = {
  punchesThrown:   number
  punchesLanded:   number
  accuracy:        number   // landed / thrown
  topSpeed:        number
  meanSpeed:       number
  damageDealt:     number
  guardUptime:     number   // 0..1
  longestBurst:    number
  medianResponse:  number   // ms
  fatigueSlope:    number   // Δ mean speed, first third → last third
  distanceMoved:   number   // shoulder-widths travelled
  handSplit:       { L: number, R: number }
}

Three things worth deciding early

  • Both clients must exchange guard state live. The landed rule needs the opponent's guard at punch time, so it belongs in the per-frame websocket payload — not reconciled afterwards. This is the one place the visualization catalog constrains the wire protocol.
  • Compute MatchPlayerStats client-side, at fight end, on the host. The host is already elected by /begin_fight; it has both event logs; and it saves you a server that parses replay blobs.
  • Version the blob. Put a { v: 1, fps, landmarkSet } header on the replay payload. Landmark sets and frame rates will change, and a replay that can't say which one it used is unreadable a month later.
